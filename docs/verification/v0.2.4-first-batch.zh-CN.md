## 修改与兼容性

- **V024-02：** layout 的 `NewHTTPServer` 不再注册 gRPC UserService，移除仅为
  该注册使用的 service 参数及手写 adapter 中直接启用的注释。HTTP 注册、登录、
  资料接口继续使用原路由与 JWT 边界；完整 gRPC 权限修复仍在 v0.4.1。
- **V024-03：** 工作 goroutine 通过单元素缓冲通道传递结果；外层持有固定的请求
  context 和 responder，避免 `Trace()` 修改 Context 时的竞态。408/499/500 及
  普通成功响应语义保留。详见 [ADR-003](../design/adr-003-http-response-ownership.zh-CN.md)。
- 默认 gRPC 关闭是有意的行为变化；依赖旧 RPC 的应用需迁移到 HTTP 或先完成
  layout README 中列出的认证、授权和验证条件。只设置端口不会恢复该服务。

## 实际验证

框架目录中的修复前命令：

```sh
go test -race -count=1 ./pkg/pi -run '^TestHandler_ServeHTTP'
```

结果：失败，race detector 报告 **6 处 data race**，包含旧 `handler.go:83`
与超时/取消分支之间的 result 读写和 err 写写冲突。日志：`baseline-handler.log`。
这是导入实际 Pi 仓库的测试结果，不是初评的隔离并发模式实验。

修复后在框架目录运行，均通过：

```sh
go test -race -count=1 ./pkg/pi -run '^TestHandler_ServeHTTP'
go test -race -count=1 ./pkg/pi -run '^(TestRouteRegistry_|TestAppGroup_)'
```

日志：`fixed-handler.log`、`fixed-routes.log`。

在 layout 目录，修复前原有测试通过：

```sh
go test -count=1 ./test ./cmd/server ./internal/middleware ./pkg/errcode
```

修复后上述四个包的 `-race` 测试通过；新增 server 测试也通过：

```sh
go test -race -count=1 ./test ./cmd/server ./internal/middleware ./pkg/errcode
go test -race -count=1 ./internal/server
```

`TestHTTPServer_DefaultUserBoundary` 使用临时配置目录、真实 HTTP 监听和 service mock，
事先占用 gRPC 端口，断言默认装配仍能成功启动；若意外注册 gRPC 服务则会启动失败。
同时验证注册/登录可达，无令牌/坏令牌的资料请求被拒绝，以及资料读写使用 JWT 中的
`user-a`，不会采用 query/body 中伪造的 `user-b`。此处没有真实数据库事务验收。

日志：`baseline-layout.log`、`fixed-layout.log`、`fixed-layout-server.log`。
首次新增 server 测试因使用了与现有 mock 不同的 gomock import 而编译失败，已改为
项目现有的 `github.com/golang/mock/gomock` 并复验通过，保留原失败日志。
macOS race 链接出现 `LC_DYSYMTAB` 警告；上述最终验证均退出 0，无 race 报告。
本批 Go 文件已 gofmt，修改范围的空白检查通过。仓库级 `git diff --check` 仍报告
先前改名文档中的尾随空格，已在修复前 patch 中核对存在，本批未顺带修改。
